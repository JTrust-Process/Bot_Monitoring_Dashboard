## CRITICAL

### C1. README instructs a deploy step that would leak the service-role key
`README.md:65` — contradicts `dashboard/.env.local.example:33-42`

README says: *"Each env var must be `NEXT_PUBLIC_*` since they're used
client-side."* That was true when only the two anon-key bots existed. It is
now false for three server-side vars: `LEAGUE_SUPABASE_URL`,
`LEAGUE_SUPABASE_SERVICE_KEY`, `LEAGUE_APPROVAL_TOKEN`.

Following it inlines the service-role key into the browser bundle — full
read/write on the League DB, RLS bypassed, plus the ability to approve
real-money orders. **No error, no visible difference from a correct deploy.**

**Verified NOT currently exploited:** the audit confirmed the live
`.env.local` has the service key un-prefixed and only the server route reads
it. The client/server split in code is correct. This is a trap for the next
deploy, not an active breach.

**Fix:** rewrite that line; add a build-time guard in `next.config.js` that
throws if any `NEXT_PUBLIC_*` value decodes to a JWT with
`"role":"service_role"`.

## HIGH

### H1. The `activeUtcHours` fix left a 17-minute hole — false Down + Recovered pair still fires every trading morning
`monitor/health_check.py:150, 236-244` · `dashboard/components/HealthDashboard.jsx:50, 55-60`

The window is `(14, 21)` tested at **hour** granularity, so it opens 14:00.
The bot's first run is **14:17**. Monitor cron is `8,23,38,53`.

EDT trading morning:
- **14:08** — window open, market open, newest run is yesterday 20:17 →
  ~1071 min vs `expected*2 = 180` → **down** → Discord 🚨
- **14:23** — bot ran at 14:17 → healthy → **"Recovered"** ✅

So the fix moved the false alarm from 13:38 to 14:08 rather than removing
it. ~165 trading days/year. Winter is clean by luck (market opens 14:30
EST, so market-hours suppression covers it).

**Fix:** express the window in **minutes** with a first-run grace:
```python
active_utc_window_min: Optional[Tuple[int, int]] = None  # (14*60+17, 20*60+17)
first_run_grace_min: int = 10
# mute unless start_m + grace <= now_m <= end_m + expected_minutes
```
Mirror in the JSX. Better: derive from the cron string in one place.

### H2. League cadence derivation is starved by the 30-row global limit — daily bots silently revert to the flat thresholds the fix removed
`dashboard/components/LeagueDashboard.jsx:13, 145-165, 252, 303-318`

`deriveCadenceMin` needs ≥3 runs per bot. Its input is one global query
`.limit(RUNS_LIMIT = 30)`, allocated by recency. A 15-min bot writes 96
rows/day, so 30 rows ≈ **7.5 hours**. `bond_research_v1` (once daily) gets
0-1 rows — never the 3 required → returns `null` → falls back to 30/120 min.

**The fix fails for exactly the bots it was written to rescue.** It appeared
to work when tested (sparse table, 30 rows spanned days) and regresses
silently as volume grows.

**Fix:** cadence needs its own data source. Either an
`expected_cadence_minutes` column on `bot_registry` (preferred — registry
truth beats inference), or per-bot queries / a `row_number() over (partition
by bot_id)` RPC. Also surface in the UI when cadence is `null`.

### H3. League staleness multipliers over-correct: a daily bot cannot go red for five days
`dashboard/components/LeagueDashboard.jsx:186-191`

`cadenceMin * 2.5` / `* 5` is sane at 15 min (37/75) and wrong at 1440:
**degraded at 2.5 days, down at 5 days.** A daily bot that dies Monday shows
Healthy until Wednesday afternoon.

Also diverges philosophically from the other two surfaces, which both use
1× → degraded, 2× → down. The Health page and League page now answer "how
late is too late" with different arithmetic.

**Fix:** additive grace, matching the rest of the system:
```js
const GRACE_MIN = 20;
const degradedMin = cadenceMin ? cadenceMin + GRACE_MIN     : HEARTBEAT_DEGRADED_MIN;
const downMin     = cadenceMin ? cadenceMin * 2 + GRACE_MIN : HEARTBEAT_DOWN_MIN;
```

### H4. Paper, live, and phantom trades are summed into the headline money figures
`dashboard/components/LeagueDashboard.jsx:1043-1053, 1248-1262, 1285-1290`

`ExposuresPanel` sums `amount_usd` across **all** open positions into
"Notional $X". `ExpensesPanel` sums `pnl_usd` across **all** trades into
"Trade P&L", then `net = pnl − expenses`. Neither reads `is_paper` (shown
per-row!) or `metadata.phantom`.

Three distortions in one number:
1. Paper mixed with live — "$8,400" may be $400 real, $8,000 simulated
2. Paper P&L netted against **real cash** expenses (Fly, Anthropic, Claude)
3. The 28 known phantom rows on `etf_rotation_v1` included

The single number you'd use to judge whether the operation is worth running
is wrong, uncaveated, in the largest type on the panel.

**Fix:** filter phantoms at the query; split live/paper in both panels;
compute Net from live only.

### H5. No dead-man's switch — a monitor that stops running looks identical to all-clear
`.github/workflows/health_check.yaml:3-6` · `monitor/health_check.py:637-757`

Alerting is push-on-bad only. Every monitor failure presents as silence, and
silence means health:
- GitHub disables `schedule:` after 60 days repo inactivity
- Missing `HEALTH_WEBHOOK_URL` prints and exits 0 (line 385)
- `save_status_state` (752) has no `try`
- Dashboard renders the last successful poll indefinitely when offline

Plus the monitor covers **only Crypto and Stock**. ETF rotation, short
watchlist, bond research, agent research have **no Discord alerting at
all** — and H3 makes the League page slow to go red.

**Fix:** (a) heartbeat the monitor to healthchecks.io / a League table and
alert on absence; (b) add a League code path reading `bot_status.last_heartbeat_at`.

## Verified correct (so the negatives can be weighed)

- **Secrets:** `.env.local` holds live credentials but is correctly gitignored at any
  depth; nothing committed. Service key appears only un-prefixed, read only server-side.
  *Hygiene note: the GitHub PAT in there is unused (`restart_enabled=False`) — a live
  credential with no purpose. Worth revoking.*
- **Approvals endpoint** — best-engineered file in the repo. `timingSafeEqual` is
  correct (iterates max length, folds length diff via XOR, no early return).
  `status=eq.pending` is an elegant DB-level double-decision guard.
  `encodeURIComponent(id)` closes PostgREST filter injection — the auditor tried to
  build a bypass and couldn't. No XSS vector found.
- **Threshold parity** — every shared constant between the two mirrored files matches
  exactly, including all ten holiday dates. The numeric drift I worried about is
  genuinely absent; the divergences are behavioural (M1, M2), not numeric.
- **DST** — correct and non-trivially so in both files. `Intl.formatToParts` with the
  `hour === "24"` midnight normalisation; `zoneinfo` on the Python side. No offset
  arithmetic. Both EST and EDT boundaries traced clean apart from H1.
- **Holiday-expiry instrumentation** — `HOLIDAY_YEARS` derived from the data itself so
  it can't drift. Mechanism right; **delivery is the weak point** — a `console.warn` and
  a GHA `print()` are both invisible in practice, and the table expires in ~5 months.
- **Alert de-duplication** — careful and unbreakable on inspection. Corrupted cache
  coerces to `healthy` so a real alert can't be swallowed; `muted` deliberately never
  persisted; malformed `last_alert_at` fails **open**.
- **Guess-audit** — every `[0]` index checked for the wrong-account pattern. All are
  preceded by explicit `.order(...)`. No unordered selection anywhere.
- `useEffect` intervals correctly cleared; `sessionStorage` try-wrapped; quantity
  formatter hand-traced against the greedy-regex failure mode; donut arithmetic correct;
  workflow `concurrency` + `if: always()` + intentional non-zero exit all sound.
